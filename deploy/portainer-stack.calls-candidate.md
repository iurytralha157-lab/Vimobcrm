# CRM candidato para o piloto de chamadas

Use `portainer-stack.calls-candidate.yml` **como uma nova stack Swarm**, por exemplo `vimob_calls_candidate`. Ela não substitui `portainer-stack.yml`. O Web e a API têm hostnames e regras Traefik próprios, mas leem e escrevem no Supabase/PostgreSQL existente do Vimob. Reserve o acesso a contas, organização e sessão de teste. A API candidata não inicia os consumidores gerais de filas; a API produtiva compatível continua responsável por webhook, outbox e supervisão das sessões compartilhadas.

## Preparação

1. Confirme que a evolução de esquema para chamadas já foi aplicada e lida de volta no Supabase usado pela produção. Não aplique migração a partir desta stack. Garanta que **todas** as réplicas da API produtiva tenham o roteamento por sessão e a allowlist do canário antes de criar/conectar a sessão de teste. Consulte o procedimento de corte em `evolution-go-hardened/CANARY.md`.
2. No workflow `docker-images.yml`, use `build_crm_candidate=true` com `use_vimob_self_hosted_data=true`. Informe `candidate_api_url=https://<VIMOB_CANDIDATE_API_HOST>`, `candidate_site_url=https://<VIMOB_CANDIDATE_WEB_HOST>` e `candidate_media_host=<EVOGO_CANARY_HOST>`. Use as imagens API/Web geradas pelo **mesmo SHA** e copie seus digests para `VIMOB_CANDIDATE_API_IMAGE` e `VIMOB_CANDIDATE_WEB_IMAGE` no formato `repo@sha256:<64 hex>`. As variáveis `NEXT_PUBLIC_*` ficam incorporadas no build do Web; alterar somente a stack não troca a API, o site ou o host de mídia usados pelo JavaScript do navegador.
3. Reserve dois FQDNs inéditos para Web e API, distintos entre si, dos hosts produtivos e do host da Evo canário. Confirme DNS, TLS, regras `Host(...)` do Traefik e a rede externa de ingresso `${TRAEFIK_NETWORK:-public}`. Não use `app.vimobcrm.com.br` ou `api.vimobcrm.com.br` para o candidato.
4. Confira a rede overlay externa que alcança o Supabase/PostgreSQL self-hosted; o padrão da stack é `VIMOB_SHARED_DATA_NETWORK=vimob`. Apenas `calls_api` ingressa nessa rede. `calls_web` encontra `calls_api` pela rede exclusiva da nova stack, sem usar o alias `api` do serviço produtivo. Passe a `DATABASE_URL` produtiva de conexão direta ou pooler em **modo sessão**, porta 5432, e reserve as conexões adicionais da API candidata (`VIMOB_CANDIDATE_DATABASE_MAX_CONNS=4` por padrão) no orçamento do banco. Não use pooler transacional 6543.
5. Crie ou confirme os Swarm secrets externos `vimob_evogo_canary_api_key` e `evogo_canary_media_hmac`. A API candidata os monta em `/run/secrets/` via `EVOLUTION_GO_CANARY_API_KEY_FILE` e `EVOGO_CANARY_CALL_MEDIA_HMAC_SECRET_FILE`. A chave da Evo canário deve ser distinta da chave da Evo produtiva; o HMAC deve ser o mesmo usado pela Evo canário. Não copie os valores para o YAML, variáveis da stack ou logs.

Copie para a nova stack os valores operacionais existentes exigidos pelo Web/API, incluindo `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_PROJECT_URL`, credenciais server-side do Supabase, JWT/JWKS, `DATABASE_URL`, e-mail, VAPID e `API_TRUSTED_PROXY_CIDRS`. Os três URLs de Supabase devem continuar apontando ao **mesmo** projeto self-hosted produtivo. `NEXT_PUBLIC_SUPABASE_URL` e a chave pública precisam coincidir com o build do Web candidato. O arquivo da stack conserva as variáveis funcionais do deploy principal; seus valores devem ser revisados para o piloto antes da criação.

## Roteamento da Evo e workers

Mantenha `EVOLUTION_GO_API_URL`, `EVOLUTION_GO_API_KEY` e `EVOLUTION_GO_IMAGE_DIGEST` da **Evo de produção** como rota padrão. Defina `EVOLUTION_GO_CANARY_SESSION_IDS` somente com UUID(s) exatos das sessões CRM de teste; `*` é rejeitado pela API. Defina `EVOGO_CANARY_HOST` com o FQDN da Evo isolada e `EVOLUTION_GO_CANARY_IMAGE_DIGEST=sha256:<digest>` dessa imagem. A stack monta os dois secrets do canário mencionados acima. A sessão fora da allowlist continua roteada à Evo produtiva; uma configuração canário incompleta falha fechada para a sessão incluída.

`API_BACKGROUND_WORKERS_ENABLED=false` é fixo na candidata. Os flags individuais dos outros workers também estão desligados. `API_WHATSAPP_CALL_RECORDING_ONLY_WORKER_ENABLED=true` inicia somente a recuperação de webhooks de chamada e a transferência de gravações dos UUIDs em `EVOLUTION_GO_CANARY_SESSION_IDS`; lista vazia ou UUID inválido impede a inicialização. Esse worker ainda consome o **mesmo banco de produção**: confirme a sessão e a política de retenção antes de permitir chamadas. `EVOLUTION_GO_BACKEND_WEBHOOK_URL` aponta para o host da API candidata. Os workers produtivos atualizados continuam consumindo o inbox compartilhado e também precisam reconhecer eventos de chamada. Nenhuma dessas opções atualiza serviços ou configuração no Portainer por si só.

## Verificação antes de tráfego

- No Portainer, confirme que criou `vimob_calls_candidate` como nova stack e que os serviços `calls_web` e `calls_api` têm uma réplica saudável cada. Compare os digests implantados e as origens compiladas do Web com os valores planejados.
- Inspecione as regras Traefik: cada host candidato deve pertencer a um único router e apresentar certificado válido. Confirme CORS da API apenas para `https://<VIMOB_CANDIDATE_WEB_HOST>`.
- Confira `/healthz` da API candidata, configuração efetiva dos dois flags de worker, montagens dos secrets e o limite de conexões. Faça somente um canário com contas consentidas e sem números/sessões produtivas.
- Se precisar recuar, remova ou desligue somente esta stack candidata e a sessão de teste. Preserve a stack produtiva e a Evo produtiva.
