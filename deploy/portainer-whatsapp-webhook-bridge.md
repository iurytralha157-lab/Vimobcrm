# Ponte HTTP temporária para o webhook da Evolution Go

Esta é uma **proposta de edição da stack `vimob-crm`**, não um deploy. O arquivo `portainer-whatsapp-webhook-bridge.patch` acrescenta `whatsapp_webhook_bridge` à mesma stack e usa âncoras YAML para herdar **exatamente** o ambiente e os Swarm secrets já definidos no serviço `api`. Nenhuma credencial é copiada para o patch. O serviço novo não executa workers gerais nem o worker de gravação, e sua rota Traefik começa **desligada**.

## Pré-condições

1. Compare o YAML efetivo no Portainer com `deploy/portainer-stack.yml`. A configuração viva já mostrou `api` com `stop-first`, enquanto o arquivo do repositório diz `start-first`; **não** substitua o YAML vivo pelo arquivo do repositório. Reproduza apenas as três adições do patch no YAML vivo: âncora em `api.environment`, âncora em `api.secrets` e o novo serviço. Se o serviço vivo não tiver `secrets`, monte somente os secrets efetivamente usados por suas variáveis `*_FILE`; nenhuma referência a arquivo pode ficar sem o mount correspondente.
2. Registre o ID da tarefa, a imagem imutável, o `UpdateConfig` e as variáveis do serviço `api` sem imprimir valores sensíveis. Faça uma comparação semântica do `api` e `web` antes/depois da edição; ambos devem permanecer idênticos. O comando local `node deploy/build-whatsapp-webhook-bridge-patch.mjs --validate` aplica o patch em uma cópia temporária, confirma essa igualdade e valida a sintaxe com `docker stack config`.
3. Defina `VIMOB_WHATSAPP_WEBHOOK_BRIDGE_IMAGE` como **imagem imutável já validada** da API que suporta `API_BACKGROUND_WORKERS_ENABLED=false`. Essa variável é independente de `VIMOB_API_IMAGE`; atualizar a API principal não pode atualizar a ponte no mesmo passo. Mantenha `VIMOB_WHATSAPP_WEBHOOK_BRIDGE_ENABLED=false`. O padrão é uma réplica com pool máximo de quatro conexões; aumente para duas apenas depois de medir folga no PostgreSQL. Confirme que a rota real da Evolution aponta para `POST /v1/whatsapp/webhook/evolution-go` no domínio da API.

## Ativação controlada

1. Adicione apenas o serviço novo à stack. Confirme `1/1`, tarefa saudável, `GET /readyz` dentro do container, release SHA esperado, conexão ao PostgreSQL e log de workers gerais desativados. Confirme que os IDs das tarefas de `api`, `web` e Evolution Go permaneceram iguais. Não crie a sessão WhatsApp de teste ainda.
2. Inspecione as rotas efetivas do Traefik. A rota da ponte é `Host(api.vimobcrm.com.br) && Path(/v1/whatsapp/webhook/evolution-go)` com prioridade `1000`; confira que a rota produtiva existente tem prioridade menor. [Traefik aplica a prioridade explícita](https://doc.traefik.io/traefik/reference/routing-configuration/http/routing/rules-and-priority/), e [no Swarm lê labels do serviço](https://doc.traefik.io/traefik/reference/install-configuration/providers/swarm/).
3. Só após `/readyz` e capacidade confirmados, mude `VIMOB_WHATSAPP_WEBHOOK_BRIDGE_ENABLED=true` na stack. Verifique que Traefik envia **somente esse caminho** à ponte. Um `GET` sem query nesse caminho deve ser rejeitado pelo método HTTP, sem criar evento; use o nome do router no access log para provar a seleção. Confirme mensagens reais entrando na fila e sendo processadas pelos workers da `api` principal, sem atraso ou erro. A mudança de label não deve substituir tarefas antigas; confira os IDs.
4. Com a ponte atendendo o webhook público, ajuste o `UpdateConfig` efetivo da `api` para `start-first` em etapa separada e verifique novamente os IDs de tarefas. Publique a imagem API imutável em outra atualização, com o ambiente e secrets já preparados. A ponte deve continuar com sua imagem fixa. Observe `api` em `/readyz`, tarefas antigas/novas, fila de webhook, mensagens recebidas e erros de Traefik. Só vincule a sessão de teste após **todas** as tarefas antigas da API saírem e a nova rota por `session_id` estar ativa.

## Limite da cobertura e recuo

O Web de produção usa `VIMOB_API_URL=http://api:8081` para chamadas feitas no servidor Next.js. Esse tráfego interno **não passa pelo Traefik** e não usa a ponte de caminho acima. Chamadas de navegador a outros caminhos da API também continuam no router principal. Portanto, a ponte protege o ingresso público do webhook durante a atualização, mas não comprova disponibilidade integral do CRM. Se a API principal ainda estiver efetivamente em `stop-first`, segure a troca da imagem até corrigir essa configuração e verificar a nova tarefa pronta; [Docker `start-first` permite sobreposição, mas não promete prontidão da aplicação](https://docs.docker.com/reference/compose-file/deploy/). A API expõe `/readyz` com ping ao banco; a ponte usa esse endpoint no healthcheck.

Se a ponte falhar **antes** da troca da API, volte `VIMOB_WHATSAPP_WEBHOOK_BRIDGE_ENABLED=false`, confirme que o router anterior retomou o webhook e só então retire o serviço. Se a nova API falhar, **mantenha a ponte ativa**, restaure a imagem anterior da API com a ordem de atualização verificada, confira `/readyz` e processamento de mensagens, depois desative a ponte. Não remova a Evolution Go produtiva, suas sessões ou seus volumes. Não altere o `VIMOB_INTERNAL_API_URL` do Web como parte desse corte: isso exige um rollout próprio do Web e validação das rotas de servidor e SSE.

O teste local do patch é `node deploy/build-whatsapp-webhook-bridge-patch.mjs --check` e `node deploy/build-whatsapp-webhook-bridge-patch.mjs --validate`. A aplicação real depende de inspeção da stack viva, segredo disponível e monitoramento durante o corte; esta proposta não foi aplicada no Portainer.
